`/highlight`의 LCK 스타일 오버레이 UI(FIRST BLOOD / SOLO KILL HUD)용 정적 에셋. 파형
애니메이션 등 나머지 오버레이 구성요소는 아직 미구현.

## 현재 구조 - 완성 배너 1장을 스킬바~미니맵 폭으로 축소해서 overlay

`panel_first_blood.png` / `panel_solokill.png`는 캔바에서 배경+이벤트 라벨 텍스트+
"POWERED BY KYVOBOT" 스폰서 문구까지 전부 그려서 만든 완성 배너 PNG다(원본 1920x120,
완전 불투명 - 투명 영역 없음). `cogs.highlight.KyvoHighlight._render_video`는
`hud["event_label"]`(`"FIRST BLOOD"` 또는 `"SOLO KILL"`) 값으로 `HUD_BANNER_PNGS` dict에서
맞는 파일을 골라 입력에 추가하고, `scale=HUD_BANNER_DISPLAY_W:HUD_BANNER_DISPLAY_H`로
축소한 뒤 `overlay` 한 번으로 합성한다 - 필터그래프에 드러텍스트나 폰트, 색상 상수, 사선
절삭 계산이 전혀 없다(이전 버전들은 아래 "이전 버전들" 절 참고).

`cogs.highlight._hud_slide_y_expr(start, end, slide, visible_y, hidden_y)`(순수 함수, 테스트
가능)가 `overlay`의 `y=` 표현식 문자열을 만든다 - `t < start`면 `hidden_y`,
`[start, start+slide)`면 `hidden_y`→`visible_y` 선형 보간(슬라이드업), `[start+slide, end)`면
`visible_y` 고정, `[end, end+slide)`면 `visible_y`→`hidden_y` 선형 보간(슬라이드다운), 그
이후는 다시 `hidden_y`. `visible_y`/`hidden_y`는 `"H-424"`처럼 `overlay`가 제공하는 심볼
(`H`=영상 높이)을 그대로 문자열에 섞어 써도 된다 - 실제 픽셀 계산은 렌더 시점에 ffmpeg가 한다.

**타이밍은 명세서의 고정값이 아니라 이 렌더의 실제 `schedule` 값을 그대로 재사용한다**:
`hud["start"] = kill_t`(0단계, 킬 순간), `hud["end"] = main_fact_start + main_fact_duration`
(3단계 사실 전달이 끝나는 시점) - `plan_kill_sequence()`/`plan_lead_in_forward()`와 똑같이
이미 계산된 값만 소비하고 새 상수를 발명하지 않는다.

## 좌표 - 라이브/리플레이 클립 실측 기반 안전구간

**x (v3, 현재) - 스킬바~미니맵 사이 폭으로 축소**: 풀와이드(x=0~1920)로 채우면 미니맵/
팀원 초상화 코너를 덮게 되는 게 v2까지의 트레이드오프였는데, 그 대신 실제로 "스킬바와
미니맵 사이 빈 공간"에 딱 맞춰 배너를 축소하는 방향으로 바꿨다. 라이브 클립 실측(스킬바
우측 끝 x≈620, 미니맵 좌측 끝 x≈1710, 1920x804 기준)으로 그 사이 폭 `HUD_BANNER_DISPLAY_W`
=1090px을 목표 크기로 잡고, `HUD_BANNER_X`=620(그 구간의 좌측 끝)에 고정 배치한다 - 구간
폭을 그대로 채우므로 "그 구간 안에서 중앙 정렬"은 자동으로 만족된다. 화면 전체 중앙
(`(W-폭)/2`)이 아니라 이 구간 자체의 좌측 끝을 쓰는 이유는, 스킬바~미니맵 구간의 중심
(x≈1165)이 화면 중심(x=960)보다 오른쪽에 있어서 "(W-폭)/2" 공식으로는 안 맞기 때문이다.

**높이도 같이 줄임**: 원본 PNG는 배경+텍스트가 하나로 합쳐진 완성 이미지라, 폭만 줄이고
높이를 그대로 두면 텍스트가 옆으로 눌린 것처럼 찌그러지고, 높이를 유지한 채 폭만 자르면
배너 좌우가 잘려나간다 - 원본 비율(1920:120 = 16:1)을 유지한 채 폭에 맞춰 축소하는 게
유일하게 텍스트가 안 찌그러지는 방법이라 사실상 선택의 여지가 없었다:
`HUD_BANNER_DISPLAY_H = 1090 * (120/1920) ≈ 68px`.

**고정 픽셀 vs 화면 비례**: 이론적으로는 화면 크기에 비례(예: 폭을 `W`의 56.8%로)하는 쪽이
더 정확하다 - 리그 오브 레전드 클라이언트 UI가 해상도에 따라 화면 비율로 스케일되는 것으로
보이기 때문이다. 다만 이번 실측은 1920x804 클립 하나뿐이라 다른 해상도에서 정말 선형
비례하는지 교차검증하지 못했고, 이 코드베이스의 실질 상한선(`MAX_OUTPUT_WIDTH`=1920) 덕에
실제 렌더 대부분이 1920 근처 폭으로 수렴한다 - 그래서 일단 1920 기준 **고정 픽셀**로
계산해뒀다. 사용자 클립 해상도가 1920과 크게 다른 경우가 흔해지면, `scale2ref` 필터로
실제 영상 폭(`W`)에 비례해서 동적으로 스케일하는 방식으로 바꿔야 한다 - 알려진 한계.

**y (v1, 폐기됨)**: 처음엔 "화면 최하단 5~10% 이내"가 라이브 클립에서 스킬/아이템 바
(x=620~1220, y=690~804, 화면 정중앙)와 무조건 겹친다는 게 실측으로 확인돼, 두 클립 타입
(라이브/리플레이) 어디에도 UI가 없는 순수 뷰포트 구간(y≈380~500, 팀원 초상화/미니맵 상단인
y=530보다 위)까지 통째로 올렸었다.

**y (v2, 현재)**: 실제 LCK 레퍼런스를 다시 보니 배너는 UI를 피해 화면 중간으로 물러나는
게 아니라 **스킬바 바로 위에 자연스럽게 붙어서** "게임화면 + 그 아래 붙은 정보 배너"처럼
보이는 게 맞다는 피드백으로 다시 내렸다. 라이브 클립 실측(스킬바 상단 y=690) 기준으로
배너 하단이 y=690에 딱 닿도록 잡았다:

```
배너 하단 목표: y=690 (라이브 스킬바 상단에 닿음)
HUD_BANNER_MARGIN_BOTTOM = H - 690 = 804 - 690 = 114
```

이 마진은 배너 높이(`HUD_BANNER_DISPLAY_H`)와 무관하게 "화면 하단에서 690까지의 거리"라서,
폭/높이를 스킬바~미니맵 사이 크기로 줄인 지금도 값이 그대로 114다. 같은 y에서 리플레이
클립의 스크러버(y=750~804)와도 60px 여유로 안 겹치는 걸 재확인해서, 클립 타입별 조건
분기 없이 하나의 좌표를 그대로 쓴다.

**v2까지는 풀와이드(x=0~1920)라서 두 클립 타입 다 우측 미니맵/팀원 초상화 코너 위를
배너가 덮었는데(미니맵 상단이 라이브 y=530/리플레이 y=606로 이 배너의 y범위 570~690과
겹침), x를 스킬바~미니맵 사이 폭(1090px)으로 좁힌 v3부터는 그 덮임 자체가 사라졌다** -
지금은 미니맵/스킬바 어느 쪽과도 안 겹치는 완전한 "빈 공간 안착"이다.

`H`를 심볼로 쓰기 때문에 다른 해상도 클립에서도 "화면 하단에서 114px 위"로 적용되지만,
실측 자체가 1920x804 클립 기준이라 해상도가 많이 다른 클립(세로 비율이 크게 다른 경우
등)에서는 재검증이 필요할 수 있다 - 알려진 한계.

## 이벤트 판별 - FIRST BLOOD / SOLO KILL

`cogs.highlight.KyvoHighlight._run_pipeline`에서 Riot API 추가 호출 없이 이미 받아온
타임라인 데이터로만 판별한다:
- **FIRST BLOOD** = 이 킬이 매치 전체에서 가장 이른 `CHAMPION_KILL`인가
  (`_extract_champion_kills`가 `timestamp_ms`로 이미 정렬해서 반환하므로, 선택된 킬의
  `timestamp_ms`가 `kills[0]`과 같은지 비교하면 된다).
- **SOLO KILL** = `assist_ids`가 비어있는가.
- 둘 다 해당하면(매치 첫 킬에 어시스트가 없는 경우) **FIRST BLOOD를 우선** 표시.
- 어느 쪽도 아니면(추격전 킬 등) HUD 자체를 안 띄운다 - `schedule`에 `"hud"` 키가 아예
  안 생기고, `_render_video`도 배너 PNG 입력을 추가하지 않아 필터그래프가 더 무거워지지
  않는다. PENTA KILL 등 나머지 이벤트는 다중 킬 백엔드가 나올 때까지 보류.

## 이전 버전들 (v1~v4, 지금은 안 씀 - 참고용)

배너를 처음부터 디자이너 완성본으로 받기 전까지는, 코드가 직접 사선 절삭 배경(`geq`
베이킹)과 텍스트(PIL, Archivo Black)를 따로 만들어 여러 겹으로 합성했다. 지금은 전부
삭제됐지만 재발 방지용으로 배운 것들을 남겨둔다:

- **알파 채널 소실**: `"color=black@0.0:..." -vf geq=...:a=...`만으로는 `geq`의 `a=`
  표현식이 실제로 적용 안 되고 항상 완전 불투명(255)으로 저장됐다 - `geq` **앞에
  `format=rgba`를 명시적으로 넣어야** 진짜 알파 플레인이 생긴다. PNG를 새로 구울 일이
  생기면(직접 만들든 디자이너에게 받든) **PIL로 열어서 `im.mode`와 코너 픽셀의 alpha 값을
  직접 찍어보고 확인할 것** - 미리보기에서 그럴싸해 보이는 것과 실제 알파 채널이 있는 건
  다르다.
- **좌우 비대칭 사선**: `between(X+Y*SLOPE, LEFT, RIGHT)` 하나의 식을 좌/우 경계에 같이
  쓰면 Y가 커질수록 한쪽만 캔버스 밖으로 일찍 빠져(사실상 수직) 반대쪽만 사선이 깊어지는
  비대칭이 생긴다 - 좌/우를 완전히 독립된 식(`gte`/`lte`를 곱해서 AND)으로 분리해야 대칭이
  나온다.
- **drawtext의 fontfile= 절대경로 이스케이프(Windows 로컬 개발 한정)**: Windows 드라이브
  콜론(`C:`)이 `-filter_complex` 옵션 구분자(`:`)와 충돌한다. 올바른 이스케이프는 슬래시로
  통일 + 콜론을 이중 백슬래시로 이스케이프(`C\\:/...`) - 리눅스 배포 서버 경로엔 이 문제
  자체가 없다. 지금은 drawtext를 아예 안 써서 무관하지만, 나중에 다시 필요해지면 이 교훈을
  참고할 것.
- **같은 상수를 배경색/글자색 두 용도로 겸용하면 배경색 변경 시 대비 버그가 생긴다**:
  한 라운드에서 배너 배경을 메인 컬러로 바꿨는데 킬 카운트 태그 글자색도 같은 상수를
  참조하고 있어서 "글자색 = 배경색"이 돼 거의 안 보이게 된 적이 있다 - 지금은 색이 전부
  디자이너의 완성 PNG에 구워져 있어 이 문제 자체가 없다.
