Static voice-line pools for `/highlight`'s 0~3단계 킬 리액션 시퀀스 (오늘 저녁 로컬 프로토타입
v1~v9에서 검증한 구조를 그대로 실서비스로 통합 - 이전의 "1단계 3인 동시 샤우팅 -> 2단계
Hype->Sub->Main 겹침 체인" 2단계 구조는 완전히 대체됐다. 그보다 더 이전의 "이상감지 ->
감정격상 -> 킬폭발" 빌드업 체인도 마찬가지 - `buildup1_*.wav`/`buildup2_*.wav`/
`main_react_*.wav` 파일은 디스크에는 남아있지만 이제 코드에서 참조되지 않는다).

## 새 구조

전체 순서: **상황 멘트 -> "어어??" -> 0단계(폭발) -> 1단계(닉네임) -> 2단계(추임새) ->
3단계(사실 전달)**.

- **상황 멘트 (선택적)**: Main이 위치/챔피언을 특정하지 않는 순수 분위기 감탄("구도
  좋은데요?" 계열)을 킬 이전 리드인의 맨 앞에 깐다.
- **"어어??" (선택적, 신규)**: Main이 짧은 "이상 감지" 반응("어어?!" 계열)을 상황 멘트
  다음, 0단계 직전에 깐다 - 상황 멘트와 0단계 사이의 완충 역할.
- **0단계 (킬 순간)**: Main + Hype + Sub 세 목소리가 `kill_t`에 완전히 동시에 순수
  "우와아아아악!!" 계열 폭발을 외친다 - 닉네임 없음.
- **1단계 (Hype 닉네임 샤우팅)**: Hype만 "{killer}~~!!" 형태로 실제 닉네임을 실시간 합성.
- **2단계 (Sub 의문형 감탄)**: Sub만 "미쳤는데요 진짜??!!" 계열 존댓말 추임새.
- **3단계 (Main 사실 전달)**: Main이 "누가 누구를 처치했는지" 실시간 GPT 생성 문장을 합성.

상황 멘트/"어어??" 둘 다 자리가 없으면(킬이 클립 맨 앞부분) 스킵되고("어어??"가 스킵되면
그 앞에 와야 하는 상황 멘트도 당연히 스킵), 0단계~3단계는 항상 재생된다.

닉네임이 실제로 필요한 자리는 정확히 두 곳뿐이다 - 1단계 Hype(닉네임 샤우팅)와 3단계
Main(사실 전달, "누가 누구를 처치했는지"). 이 둘만 렌더당 ElevenLabs 실시간 호출로
합성하고(`cogs.highlight.KyvoHighlight._synthesize_voice_line`, 렌더당 정확히 2회), 나머지
네 자리(0단계 세 목소리 + 2단계 Sub)는 닉네임이 필요 없는 순수 감정 표현이라 이 폴더의
정적 풀에서 고른다(`random.choice`, 기존 SFX 풀과 같은 glob 패턴).

**기술적 판단 - 왜 1단계도 실시간 TTS 하나를 더 쓰는지**: "1단계 샤우팅에 실제 닉네임이
들어가야 한다"는 요구사항이 있었고, 닉네임은 정적 파일로 미리 구워둘 수 없다(매 킬마다
다름). 선택지는 (a) 1단계에서 닉네임을 포기하고 순수 감탄사만 쓰거나, (b) 관련된 한
목소리만 실시간 TTS로 닉네임을 외치게 하는 것 - (b)를 택했다. 한 목소리만 추가로 실시간으로
돌리면 렌더당 TTS 호출이 기존 1회에서 2회로만 늘고(3단계 Main의 사실 서술은 원래도
실시간이었음), 전부 실시간으로 만드는 것보다 훨씬 저렴하면서도 "닉네임이 실제로 들린다"는
요구사항은 그대로 충족된다. 문자 수 자체도 짧은 외침이라 비용 부담은 크지 않다.

**닉네임 발음 표기 - 왜 음절을 늘려 쓰지 않는지**: 처음엔 "장이이인정시이인!!"처럼 음절을
반복해서 늘려 썼는데, TTS 발음 경계와 안 맞아 "장애~인정신"처럼 들리는 문제가 로컬
프로토타입에서 확인됨. 이름 음절은 그대로 두고 끝에 물결표만 붙이는 방식이 더 자연스러웠고,
여기에 오디오 후처리 볼륨 스웰(`KyvoHighlight._apply_nickname_swell` - 뒷부분만 서서히
커짐, 이름 자체는 안 건드림)을 결합해서 "길게 끄는 느낌"을 흉내낸다.

## Pools

### 상황 멘트 (킬 이전 리드인 1/2)

- **`pre_buildup_*.wav`** (LCK_Main_caster, `[curious]` 태그) - 위치/챔피언/상황을 전혀
  특정하지 않는 순수 분위기 감탄만 골랐다.
  - `pre_buildup_a.wav`: "구도 좋은데요?"
  - `pre_buildup_b.wav`: "분위기가 심상치 않은데요?"
  - `pre_buildup_c.wav`: "긴장감이 느껴지는데요?"

  **환각 위험 차단**: 이 기능을 요청할 때 예시로 "탑쪽은 신경전이 벌어지는 중이네요"(특정
  라인 지목) 같은 문구가 같이 제시됐는데, 이건 채택하지 않았다 - 킬이 탑에서 안 났으면
  명백히 지어낸 사실이 되고, `SYSTEM_PROMPT`가 지키는 "목록에 없는 내용은 절대 지어내지
  마라" 원칙과 정면으로 어긋난다. 어떤 클립에 붙어도 항상 사실일 수 있는 문장만 골랐다
  (예전 `BUILDUP_TEXT`와 동일한 원칙).

### "어어??" (킬 이전 리드인 2/2, 신규)

- **`buildup1_a.wav`** (LCK_Main_caster) - 이 구조로 재설계되기 훨씬 전, "이상감지 ->
  감정격상 -> 킬폭발" 빌드업 체인 시절에 만들어뒀던 정적 풀을 그대로 재사용했다(새 TTS
  없음) - 이미 짧고("짧게" 요구사항 충족) 내용도 "이상 감지" 반응이라 이 역할에 정확히
  맞았다.
  - `buildup1_a.wav`: "어어?!"

  **풀 조정**: 원래 `buildup1_b.wav`("어?! 뭔가...?!")도 `EOEO_POOL`에 같이 있었는데,
  "어어?!" 계열을 우선 쓰라는 요청으로 `buildup1_a.wav` 하나로만 좁혔다. `buildup1_b.wav`
  파일 자체는 디스크에 남아있지만 `EOEO_POOL`/`EOEO_TEXT`에서 더는 참조되지 않는다.

### 0단계 (킬 순간 동시 폭발, 닉네임 없음)

**재녹음 이력 (여러 차례)**: 처음엔 "찔끔"하다는 피드백으로 여러 짧은 감탄 문장을 이어붙여
길이를 3~4배까지 늘렸는데(예: "우와아아악!!! 대박입니다, 진짜!! 완전 미쳤어요!!..."),
`silencedetect`로 실측해보니 문장 경계마다 TTS가 자연스러운 숨쉬기 무음을 넣어서 세 목소리의
무음 타이밍이 서로 안 맞았다 - "계속 겹쳐 울리는 게 아니라 끊기는 지점마다 한둘만 들리는"
문제의 실제 원인이었다. 그래서 문장을 이어붙이는 대신 감탄사 자체의 모음을 늘여 발음하는
방식으로 바꿨다(닉네임과 달리 의미 있는 고유명사가 아니라 순수 감탄사라 안전). 모음을
과하게(25~30개) 늘이면 그 안에서도 다시 끊김이 생기고, 15개 안팎으로 줄여도 정밀
측정(20ms RMS 프레임 기준, -30dB 이상 깊은 딥)으로는 여전히 파일당 여러 곳 짧은 딥이
남는다는 게 추가로 확인됨 - `silencedetect(noise=-35dB:d=0.15)` 하나만으로는 0.15초보다
짧은 딥을 못 잡는다는 한계 때문이었다. 최종적으로 모음 개수를 6~10개로 더 줄이고, 파일당
여러 번(최대 12~14회) 생성해서 "0.15초 이상 무음 0곳 + 정밀 기준 깊은 딥 0곳"을 만족하는
테이크를 자동 채택하는 방식으로 6개 파일 전부 재녹음했다(ElevenLabs Creator 티어, 문자
한도 121,000 - 재시도를 넉넉히 돌릴 수 있어 가능했다). `sub_shout_b`는 "허"+"어" 계열
음소가 유독 끊기기 쉬워서(28회 시도해도 매번 1곳 남음) "히"+"이" 계열로 바꾸니 7회 만에
해결됐다.

- **`main_explode_*.wav`** (LCK_Main_caster) - 이 역할의 정적 풀이 예전엔 없어서 새로 녹음.
  - `main_explode_a.wav`: "우와아아아아아아아아아아악!!" (1.52s)
- **`hype_*.wav`** (LCK_Hype_Reaction) - 구조가 여러 번 바뀌는 동안(예전엔 "메인 종료 후
  순차 재생", 그 다음엔 "1단계 3인 동시 샤우팅") 내용 자체는 계속 짧은 순수 폭발형
  감탄사였어서 파일 자리는 안 바뀌고 계속 재사용된다.
  - `hype_a.wav`: "와아아아아아아아아아아악!!" (2.08s)
  - `hype_b.wav`: "우와아아아아아아아아!!" (1.76s)
  - `hype_c.wav`: "으아아아아아아악!" (1.36s)

  **버그 수정 이력**: `hype_a.wav`/`hype_b.wav`는 원래 각각 "미쳤다!!"/"대박이다!!"로 반말체
  녹음돼 있었다 - `cogs.highlight.SYSTEM_PROMPT`를 존댓말 전용으로 다시 쓴 라운드에서
  `hype_b.wav`만 TODO로 표시하고 넘어갔었는데, `hype_a.wav`도 같은 문제였다는 게 나중에
  확인됨(`hype_c.wav`만 우연히 존댓말이라 프로덕션에서 2/3 확률로 반말이 실제로 나가고
  있었음에도 한동안 못 잡았음). 감탄사로 재녹음하면서 존댓말 문제 자체는 자연히 해소됨
  (감탄사에는 종결어미가 없다).
- **`sub_shout_*.wav`** (Lck_Sub_Analyst) - 닉네임 없는 순수 폭발형 감탄사. 기존
  `sub_*.wav`(분석가 멘트)는 이 역할에 안 맞아서 새로 녹음했던 것을 재사용.
  - `sub_shout_a.wav`: "우와아아아아아아아아!!" (1.60s)
  - `sub_shout_b.wav`: "히이이이이이이이이!!" (1.44s)

### 1단계 (Hype 닉네임 샤우팅)

정적 풀이 아니라 `HYPE_NICKNAME_SHOUT_TEMPLATE`("{killer}~~!!")을 실시간 TTS로 합성한
뒤 `_apply_nickname_swell`로 후처리(뒷부분 볼륨 스웰) - 유일하게 닉네임이 들어가는 1단계
목소리. 0단계가 이미 "우와아아아악!!" 감탄사를 셋이 같이 외쳤으므로 여기선 닉네임만, 감탄사
중복 없음.

### 2단계 (Sub 의문형 감탄)

- **`sub_question_*.wav`** (Lck_Sub_Analyst) - 의문형 감탄, 존댓말.
  - `sub_question_a.wav`: "진짜 돌았는데요??!!"
  - `sub_question_b.wav`: "이게 실화예요??!!"
  - `sub_question_c.wav`: "미쳤는데요 진짜??!!" (신규 - 로컬 프로토타입에서 가장 검증된 표현을
    실서비스에도 추가)

### 3단계 (Main 사실 전달)

정적 풀이 아니라 `cogs.highlight._generate_commentary`(GPT 실시간 생성, "누가 누구를
처치했는지" 사실 서술)를 실시간 TTS로 합성 - 조사 검증(`_i_or_ga`/`_eul_or_reul`,
`_commentary_names_killer`)도 이 역할을 따라 3단계로 옮겨왔다(이 문장의 역할은 그대로,
담당 목소리만 여러 라운드에 걸쳐 Main -> Hype -> Main으로 옮겨다녔음).

모두 ElevenLabs `eleven_v3`, `[excited][shouts]`(샤우팅류) 또는 `[impressed]`/`[curious]`
태그로 생성.

## Mixing - 해설 음성 게인(`VOICE_MIX_GAIN_DB`)과 alimiter `level=false`

함성은 그대로 두고 해설(0~3단계 6~7자리 전부)만 키워달라는 요청으로 `VOICE_MIX_GAIN_DB`를
각 목소리의 `adelay` 체인에 `volume=Xdb`로 얹었다. 처음 0~9dB를 스윕했을 때 최종 피크가
게인에 비례하지 않고 특정 값(3.0/5.5/6.0/8.0/9.0dB)에서만 콕 집어 0dBFS를 살짝 넘는
불안정한 패턴이 나왔는데, 원인은 게인이 아니라 **ffmpeg `alimiter`의 `level`(자동 레벨
보정) 옵션이 기본값 `true`였던 것** - 리미터가 게인을 깎은 만큼 출력을 다시 끌어올려서
`limit`이 정작 하드 천장으로 작동하지 않고 있었다(입력 게인이 달라질 때마다 보정량도
달라지니 결과가 비선형적으로 튄 것). `level=false`로 명시적으로 꺼서 진짜 하드 리미터로
만들었더니 게인을 0~10dB 전부 스윕해도 피크가 -3.2~-3.8dB(=`SFX_LIMITER_CEILING`=0.65의
이론치 -3.74dB와 거의 일치)로 안정적으로 고정됨을 확인 - 그 뒤로는 게인을 얼마로 잡든
클리핑 위험이 사실상 사라져서, `SFX_MIX_GAIN_DB`(함성, 6.0dB)와 맞춰 `VOICE_MIX_GAIN_DB`도
6.0dB로 잡았다. `level=false` 자체는 이 세션 훨씬 이전(로컬 프로토타입 단계)에 한 번 배운
교훈이었는데 실제 프로덕션 필터그래프로 옮길 때 빠졌던 것으로 보인다.

## Scheduling

킬 이전 리드인 두 단계(상황 멘트 -> "어어??")는
`cogs.highlight.plan_lead_in_forward(kill_t, pre_buildup_dur, eoeo_dur, start_offset, mid_gap,
end_gap)`(순수 함수, 테스트 가능)로 계산한다 - **`kill_t` 역산이 아니라 클립 시작(t=0) 기준
정방향 배치**. 상황 멘트는 `start_offset`(`PRE_BUILDUP_START_OFFSET_SEC`, 기본 0.4초) 뒤에
시작하고, "어어??"는 상황 멘트가 끝난 뒤 `mid_gap`(`PRE_BUILDUP_GAP_SEC`)만큼 쉬고 이어진다.
`kill_t`와 안 겹치는지(`end_gap`=`EOEO_GAP_SEC`만큼 여유)만 검사해서, 자리가 없으면(클립이
너무 짧거나 `kill_t`가 너무 이르면) "어어??"부터 스킵하고, 그래도 안 맞으면 상황 멘트도
스킵한다.

**이전 설계(`plan_lead_in_start`, 폐기됨)와의 차이**: 원래는 `kill_t`에서 거꾸로 역산해서
"어어??"를 킬 직전에, 상황 멘트를 그 앞에 배치했는데, 이러면 킬이 클립 뒷부분에 있을수록
상황 멘트가 "클립 시작 직후"가 아니라 "킬 몇 초 전"에 나와버리는 문제가 있었다(실측: 15.3초
클립, `kill_t=8.564`에서 상황 멘트가 t=5.92s에 나옴 - "영상 시작하자마자"라는 의도와 어긋남).
`plan_lead_in_forward`로 바꾼 뒤에는 같은 클립에서 상황 멘트가 t=0.4s, "어어??"가 t=2.36s로
클립 시작 직후에 확실히 붙는다.

`cogs.highlight.plan_kill_sequence()`(순수 함수, 테스트 가능)가 0~3단계 전체 타이밍을
계산한다:

```
t1 = stage0_dur * STAGE_OVERLAP_RATIO
t2 = t1 + stage1_dur * STAGE_OVERLAP_RATIO
t3 = t2 + stage2_dur * STAGE_OVERLAP_RATIO
```

(반환값은 `kill_t` 기준 상대 오프셋 - 호출부에서 `kill_t + t1` 식으로 절대 시각으로 바꿔
쓴다.) `stage0_dur`는 0단계 세 목소리(Main/Hype/Sub) 중 가장 길게 끝나는 것의 길이 -
셋 다 `kill_t`에서 동시에 시작하므로 `max(세 duration)`.

`STAGE_OVERLAP_RATIO`(현재 0.65)는 "앞 단계 목소리가 65% 지점까지 왔을 때 다음 단계가
끼어든다"는 뜻 - 완전 동시(뭉개짐)도 완전 순차(지루함)도 아닌 지점을 노린 값이며, 로컬
프로토타입 v5~v9에서 여러 값을 직접 들어보고 검증됐다. 정확히 "얼마나 겹쳐야
자연스러운가"는 결국 사람이 들어봐야 판단할 수 있는 영역이라, 이 상수 하나만 바꾸면 쉽게
다시 튜닝할 수 있게 남겨뒀다.

**0단계 길이와 1/2/3단계 상호 간격은 수학적으로 무관함(실측 확인)**: 0단계를 3~4배 더
늘린 라운드에서 "1/2/3단계가 안 겹치고 구분됐으면" 하는 피드백이 있었는데, 위 식을 보면
`t2-t1 = stage1_dur*RATIO`, `t3-t2 = stage2_dur*RATIO`로 둘 다 `stage0_dur`가 아예
등장하지 않는다 - 즉 0단계가 아무리 길어져도 1/2/3단계끼리 서로 얼마나 겹치는지는 전혀
안 바뀌고, 셋 다 `kill_t` 기준으로 통째로 더 뒤로 밀릴 뿐이다. 실측으로도 재확인됨(stage0_dur
6.16s인 렌더에서 `t2-t1=1.25=hype_nickname_dur*0.65`, `t3-t2=0.99=sub_question_dur*0.65`
그대로 - 0단계 length 변화의 영향 0). 그러니 "1/2/3단계가 여전히 겹친다"는 인상은 새로
생긴 버그가 아니라 처음부터 있던 `STAGE_OVERLAP_RATIO=0.65`의 의도된 설계(각 단계가 앞
단계 65% 지점에 끼어듦) 그대로다 - 0단계가 길어져서 전체 시작이 늦어진 것과 섞여서 더
도드라지게 느껴졌을 수는 있다. 겹침 자체를 줄이고 싶으면 `STAGE_OVERLAP_RATIO`를 1.0에
가깝게(예: 0.85~0.95) 올리는 게 다음 단계.

**알려진 한계**: 고정 초가 아니라 실측 길이 기반이라, 킬러 닉네임이 길어지면(1단계 자체
길이 증가) 뒤따르는 간격도 비례해서 늘어난다 - 로컬 프로토타입 실측으로 15음절 닉네임에서
전체 렌더 길이가 3글자 닉네임 대비 +50%까지 늘어지는 걸 확인함. Riot 닉네임 자체를 제한할
수는 없어서(강제 불가) `/highlight` 명령어의 `video` 파라미터 설명에 부드러운 안내 문구만
추가했다 - 강제로 막지는 않는다.
